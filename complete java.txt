

### **1. What happens when you run a Java program from compilation to execution?**

**Interview Answer:**

> “When we run a Java program, it goes through four main phases — compilation, class loading, bytecode verification, and execution by the JVM.”

**Detailed Steps:**

1. **Compilation:**

   * `.java` → `.class`
   * Java compiler (`javac`) converts source code into platform-independent **bytecode**.
2. **Class Loading:**

   * JVM loads `.class` files into memory using the **ClassLoader**.
3. **Bytecode Verification:**

   * Ensures the bytecode follows JVM security rules.
4. **Execution:**

   * JVM executes bytecode using the **Just-In-Time (JIT)** compiler, which translates frequently used bytecode into native machine code for faster performance.

**Example Line (Interview-style):**

> “Java uses a ‘compile once, run anywhere’ model — compilation creates bytecode, and JVM interprets or JIT-compiles it to native instructions at runtime.”

---

### **2. Explain the difference between JDK, JRE, and JVM**

| Component                          | Description                                                           | Includes                                     |
| ---------------------------------- | --------------------------------------------------------------------- | -------------------------------------------- |
| **JVM (Java Virtual Machine)**     | Executes Java bytecode and provides runtime environment.              | Part of JRE                                  |
| **JRE (Java Runtime Environment)** | Contains JVM + libraries required to run Java applications.           | JVM + core libraries                         |
| **JDK (Java Development Kit)**     | Full development environment — allows compiling and running programs. | JRE + compiler + tools (javac, jar, javadoc) |

**Interview Answer:**

> “JVM is the engine that executes Java code. JRE provides the libraries and JVM needed to run applications. JDK is the complete toolkit that includes the JRE and developer tools like the compiler.”

---

### **3. How does the JVM load and execute classes?**

**Interview Answer:**

> “The JVM loads classes using the ClassLoader subsystem, verifies them for security, prepares memory for class variables, resolves references, and finally initializes the class. Then the bytecode is executed by the execution engine.”

**Steps (Class Loading Process):**

1. **Loading:**
   ClassLoader loads `.class` files into memory.
2. **Linking:**

   * Verification
   * Preparation (allocates memory for static variables)
   * Resolution (resolves symbolic references)
3. **Initialization:**
   Executes static initializers and static blocks.
4. **Execution:**

   * Handled by the **Execution Engine**, which includes:

     * **Interpreter**: Executes bytecode line by line.
     * **JIT Compiler**: Converts hot code paths into native machine code for speed.

---

### **4. What is ClassLoader? How many types of class loaders exist in Java?**

**Interview Answer:**

> “A ClassLoader in Java is responsible for loading classes into memory dynamically at runtime. It forms part of the JVM’s class loading subsystem.”

**Types of ClassLoaders:**

1. **Bootstrap ClassLoader:**

   * Loads core Java classes (`java.lang`, `java.util`).
2. **Extension (Platform) ClassLoader:**

   * Loads classes from the `ext` directory or platform libraries.
3. **Application (System) ClassLoader:**

   * Loads classes from the classpath (`classpath` environment variable).
4. *(Optional)* **Custom ClassLoaders:**

   * Developers can extend `ClassLoader` to load classes from custom locations (e.g., network or encrypted sources).

**Example Interview Line:**

> “Class loading follows a *parent delegation model*, where each loader delegates to its parent first to prevent loading core classes multiple times.”

---

### **5. What is the difference between stack and heap memory?**

| Feature               | **Stack**                                 | **Heap**                       |
| --------------------- | ----------------------------------------- | ------------------------------ |
| **Stores**            | Method calls, local variables, references | Objects and instance variables |
| **Access Speed**      | Faster                                    | Slower                         |
| **Memory Allocation** | Static                                    | Dynamic                        |
| **Thread Safety**     | Thread-specific                           | Shared across threads          |
| **Managed By**        | JVM automatically (per thread)            | Garbage Collector              |

**Interview Answer:**

> “The stack stores method calls and local variables, while the heap stores objects. Each thread has its own stack, but the heap is shared among all threads. Objects in the heap are managed by the garbage collector.”

---

### **6. Explain how Garbage Collection works internally.**

**Interview Answer:**

> “Garbage Collection (GC) in Java automatically removes objects that are no longer reachable from any live thread or static reference, freeing up heap memory.”

**Internal Working:**

* JVM uses **reachability analysis** — objects reachable from GC roots (like local variables, active threads, static fields) are kept alive.
* Unreachable objects are marked and collected.
* Common algorithms:

  * **Mark and Sweep:** Marks live objects, sweeps away dead ones.
  * **Generational GC:** Divides heap into Young, Old (Tenured), and Permanent generations.
  * **JIT Optimization:** Young objects are collected more frequently since most die young.

**Interview Tip:**

> “Developers don’t explicitly free memory in Java — the GC tracks object reachability and reclaims unused memory automatically.”

---

### **7. What are strong, weak, soft, and phantom references in Java?**

| Type                  | Description                                                 | Garbage Collection Behavior                 |
| --------------------- | ----------------------------------------------------------- | ------------------------------------------- |
| **Strong Reference**  | Default reference type (e.g., `Object obj = new Object();`) | Never collected while reachable             |
| **Soft Reference**    | Used for memory-sensitive caches                            | Collected *only when memory is low*         |
| **Weak Reference**    | Doesn’t prevent GC; used in WeakHashMap                     | Collected *as soon as no strong refs exist* |
| **Phantom Reference** | Used for post-mortem cleanup (with ReferenceQueue)          | Collected only *after finalization*         |

**Interview Answer:**

> “Java provides different reference types for memory control — strong references keep objects alive, soft and weak references allow the GC to reclaim memory more flexibly, and phantom references are used for cleanup operations before final disposal.”

---

### **8. How can you make an object eligible for garbage collection?**

**Interview Answer:**

> “An object becomes eligible for GC when there are no more strong references pointing to it.”

**Examples:**

1. **Nullifying reference:**

   ```java
   obj = null;
   ```
2. **Reassigning reference:**

   ```java
   obj1 = new Object(); // old object becomes unreachable
   ```
3. **Objects going out of scope:**

   * Local variables after method completion.
4. **Isolated objects (island of isolation):**

   ```java
   A a = new A();
   B b = new B();
   a.b = b;
   b.a = a;
   a = b = null; // both eligible for GC
   ```

---

### **9. What are memory leaks in Java? How can you detect and prevent them?**

**Interview Answer:**

> “A memory leak in Java occurs when objects are no longer needed but are still referenced, preventing garbage collection. Over time, this leads to increased memory usage and potential `OutOfMemoryError`.”

**Common Causes:**

* Static references holding large objects.
* Unclosed resources (sockets, streams, connections).
* Improper listener or cache management.

**Detection Tools:**

* **VisualVM**, **JProfiler**, **Eclipse MAT**, **YourKit** — used to analyze heap dumps.

**Prevention:**

* Use try-with-resources for closing streams.
* Nullify long-lived references.
* Use WeakReferences in caches or listeners.

**Example:**

> “Using a static collection that keeps adding objects without removing them is a classic memory leak pattern.”

---

### **10. Difference between final, finally, and finalize()**

| Keyword        | Purpose                                                                             | When Used                 |
| -------------- | ----------------------------------------------------------------------------------- | ------------------------- |
| **final**      | Prevents modification (variable reassignment, method overriding, class inheritance) | Compile-time              |
| **finally**    | Used in try-catch to execute cleanup code                                           | Runtime (always executes) |
| **finalize()** | Method called by GC before object deletion (deprecated after Java 9)                | Runtime (before GC)       |

**Interview Answer:**

> “`final` is a keyword for immutability, `finally` is a block for cleanup after try-catch, and `finalize()` is a deprecated method once used for cleanup before GC. Modern Java uses try-with-resources instead of finalize().”

### **1. What are the new features introduced in Java 8 and Java 11?**

**Java 8 (2014):**
Java 8 was a major release that introduced functional programming concepts.
Key features include:

* **Lambda Expressions** – Enables functional-style coding with cleaner syntax.
* **Stream API** – For processing collections in a declarative way.
* **Functional Interfaces** – Single abstract method interfaces used with lambdas.
* **Optional Class** – Helps avoid `NullPointerException`.
* **Default and Static Methods** – Allows adding methods to interfaces without breaking existing code.
* **New Date and Time API** – Immutable and thread-safe replacement for `Date` and `Calendar`.

**Java 11 (2018):**
Java 11 focused on simplification and modernization:

* **New String methods** like `isBlank()`, `lines()`, `strip()`, `repeat()`.
* **Local variable syntax for lambda parameters** (`var`).
* **HTTP Client API** – Modern replacement for `HttpURLConnection`.
* **Single-file source code execution** (`java Hello.java`).
* **Removed legacy modules** like Java EE and CORBA.

### **2. Explain Lambda Expressions and Functional Interfaces.**

A **lambda expression** is essentially an anonymous function — it lets us write concise implementations for interfaces with a single abstract method.
Example:

```java
Runnable r = () -> System.out.println("Running thread...");
```

This replaces anonymous inner classes and makes code cleaner.

A **functional interface** is an interface with exactly one abstract method.
It can have any number of default or static methods.
Examples include `Runnable`, `Callable`, `Comparator`, and `Function`.
They’re usually annotated with `@FunctionalInterface`.

---

### **3. What are default and static methods in interfaces?**

Before Java 8, interfaces couldn’t have any implementation.
Java 8 introduced:

* **Default methods:** Have a body and can be overridden by implementing classes.
  Used to add new functionality without breaking old implementations.

  ```java
  default void log() {
      System.out.println("Default logging");
  }
  ```
* **Static methods:** Belong to the interface itself, not to any instance.

  ```java
  static void printInfo() {
      System.out.println("Interface info");
  }
  ```

---

### **4. What is the difference between abstract classes and interfaces?**

| Aspect       | Abstract Class                          | Interface                                                     |
| ------------ | --------------------------------------- | ------------------------------------------------------------- |
| Methods      | Can have abstract + concrete methods    | Till Java 7 only abstract, from Java 8 default/static allowed |
| Variables    | Can have instance and static variables  | Only `public static final` constants                          |
| Inheritance  | Single inheritance                      | Multiple inheritance                                          |
| Constructors | Allowed                                 | Not allowed                                                   |
| Use case     | For “is-a” relationship and shared code | For defining a contract or behavior                           |

**Example:**
If I want to define a base class with partial implementation → use **abstract class**.
If I want to define a capability (like `Comparable` or `Serializable`) → use **interface**.

### **5. What is the purpose of the Optional class in Java 8?**

`Optional` is a container object used to represent the **presence or absence** of a value — it helps avoid `NullPointerException`.
Example:

```java
Optional<String> name = Optional.ofNullable(getName());
name.ifPresent(System.out::println);
```

It provides methods like `isPresent()`, `ifPresent()`, `orElse()`, `orElseThrow()` to handle nulls safely and more expressively.

---

### **6. What is Stream API? Difference between intermediate and terminal operations.**

The **Stream API** allows functional-style operations on collections.
Instead of writing loops, we chain operations like filtering, mapping, and reducing.

Example:

```java
List<String> names = list.stream()
                         .filter(n -> n.startsWith("A"))
                         .map(String::toUpperCase)
                         .collect(Collectors.toList());
```

* **Intermediate operations** (like `filter`, `map`, `sorted`) return another stream — they are lazy.
* **Terminal operations** (like `collect`, `forEach`, `count`) produce a result or a side effect and close the stream.

---

### **7. How does method overloading resolution work in Java?**

Method overloading is resolved **at compile time** (static binding).
When multiple methods match, the compiler selects the most specific one based on:

1. **Exact type match.**
2. **Widening conversion** (e.g., `int` → `long`).
3. **Boxing/unboxing** (e.g., `int` → `Integer`).
4. **Varargs** as the last option.

If two methods are equally specific (like boxing vs varargs), the compiler throws an ambiguity error.

---

### **8. What are autoboxing and unboxing? What are potential pitfalls?**

* **Autoboxing:** Automatically converting a primitive type to its wrapper object (e.g., `int` → `Integer`).
* **Unboxing:** Automatically converting a wrapper object to a primitive.

Example:

```java
Integer num = 10; // autoboxing
int n = num;      // unboxing
```

**Pitfalls:**

* Can cause **NullPointerException** when unboxing null values.
* Can impact **performance** due to unnecessary object creation in loops or collections.

---

### **9. What are varargs (`...`) and how does Java resolve method calls with them?**

**Varargs** allow you to pass a variable number of arguments to a method.
Internally, they’re treated as arrays.

Example:

```java
void print(String... names) { }
```

When resolving overloaded methods, Java prefers:

1. Exact match
2. Widening
3. Boxing
4. Varargs *(least preferred)*

If more than one match is equally valid, you get a compile-time ambiguity.

---

### **10. How does the equals() and hashCode() contract work?**

Both methods are crucial for objects stored in **hash-based collections** like `HashMap` or `HashSet`.

**Contract:**

1. If two objects are equal using `equals()`, they must return the same `hashCode()`.
2. If two objects have the same `hashCode()`, they may or may not be equal.
3. `equals()` should be reflexive, symmetric, transitive, and consistent.

Example:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Person)) return false;
    Person p = (Person) o;
    return id == p.id;
}

@Override
public int hashCode() {
    return Objects.hash(id);
}
```

If this contract is violated, objects may not be found correctly in hash-based collections.

### **1. Explain the four pillars of OOP with real-life Java examples.**

**(1) Encapsulation** – Hiding internal data and exposing only what’s necessary through getters/setters.
Example:

```java
class Account {
    private double balance;
    public double getBalance() { return balance; }
    public void deposit(double amount) { balance += amount; }
}
```

**Real-life analogy:** ATM – you can deposit or withdraw but can’t directly access the bank’s database.

---

**(2) Inheritance** – Acquiring properties and behavior from a parent class.
Example:

```java
class Vehicle { void start() {} }
class Car extends Vehicle { void openDoor() {} }
```

**Analogy:** A car “is-a” vehicle and inherits its functionality.

---

**(3) Polymorphism** – The ability of an object to take many forms (same interface, different implementation).
Example:

```java
Vehicle v = new Car(); 
v.start(); // Calls Car’s version of start()
```

**Analogy:** A person can be a student at college, an employee at work, a customer in a shop.

---

**(4) Abstraction** – Hiding complex implementation details and exposing only essential features.
Example:

```java
abstract class Payment {
    abstract void pay();
}
class CreditCardPayment extends Payment {
    void pay() { System.out.println("Paid via credit card"); }
}
```

**Analogy:** When you drive a car, you use the steering and pedals without knowing how the engine works.

---

### **2. What is the difference between encapsulation and abstraction?**

| Concept           | Description                                                           | Example                          |
| ----------------- | --------------------------------------------------------------------- | -------------------------------- |
| **Encapsulation** | Hiding data using access modifiers and controlling access via methods | Private fields + getters/setters |
| **Abstraction**   | Hiding complexity by exposing only essential behavior                 | Abstract classes, interfaces     |

**Short answer:**
Encapsulation is about **data hiding**, while abstraction is about **detail hiding**.

---

### **3. How do you achieve polymorphism in Java?**

Polymorphism is achieved in **two ways**:

1. **Compile-time polymorphism (method overloading)** – Same method name, different parameter lists.

   ```java
   void print(int n) {} 
   void print(String s) {}
   ```
2. **Runtime polymorphism (method overriding)** – Subclass provides a specific implementation of a parent method.

   ```java
   class Animal { void sound() {} }
   class Dog extends Animal { void sound() { System.out.println("Bark"); } }
   ```

---

### **4. What is the difference between compile-time and runtime polymorphism?**

| Type             | Achieved By        | Binding Time               | Example                            |
| ---------------- | ------------------ | -------------------------- | ---------------------------------- |
| **Compile-time** | Method Overloading | Compile-time               | `print(int)` vs `print(String)`    |
| **Runtime**      | Method Overriding  | Runtime (dynamic dispatch) | `Animal a = new Dog(); a.sound();` |

**Key point:** Overloading = early binding, Overriding = late binding.

---

### **5. What is method overriding and what rules must be followed?**

**Definition:**
When a subclass provides its own implementation of a method already defined in the parent class.

**Rules:**

* Method name, return type, and parameters must be **identical**.
* Access level **cannot be more restrictive** (can be more permissive).
* The overriding method **cannot throw broader checked exceptions**.
* Only **inherited methods** can be overridden (not `private`, `final`, or `static` ones).
* Occurs at **runtime** — it’s an example of dynamic polymorphism.

---

### **6. Can constructors be overridden? Why or why not?**

No, **constructors cannot be overridden**.
Because:

* They are **not inherited** by subclasses.
* Each class has its own constructor to initialize its own state.
  However, **constructors can be overloaded** (same name, different parameters).

Example:

```java
class Person {
    Person() {}
    Person(String name) {}
}
```

---

### **7. How does inheritance affect constructors and object creation order?**

When an object of a subclass is created:

1. The **parent class constructor executes first**, then the child’s.
2. This happens because each subclass constructor **implicitly calls `super()`** as the first statement.

Example:

```java
class A { A() { System.out.println("A"); } }
class B extends A { B() { System.out.println("B"); } }
```

Output:

```
A
B
```

**Reason:** The base class must be fully constructed before the child’s members can be initialized.

---

### **8. What are access modifiers in Java? How do they work in inheritance?**

**Access modifiers:** `public`, `protected`, `default` (package-private), and `private`.

| Modifier      | Visible To                | Inheritance Behavior     |
| ------------- | ------------------------- | ------------------------ |
| **public**    | Everywhere                | Inherited                |
| **protected** | Same package + subclasses | Inherited                |
| **default**   | Same package only         | Inherited within package |
| **private**   | Same class only           | Not inherited            |

**Rule:**
An overriding method **cannot reduce visibility** (e.g., can’t change `public` to `protected`).

---

### **9. What is composition vs inheritance? Which one do you prefer and why?**

**Inheritance:**
Represents an “is-a” relationship.
Example: `Car extends Vehicle`.
**Composition:**
Represents a “has-a” relationship.
Example:

```java
class Car {
    Engine engine = new Engine();
}
```

**Preference:**
Prefer **composition over inheritance** because:

* It provides better **flexibility** and **loose coupling**.
* You can **change behavior at runtime** by composing different objects.
* Inheritance tightly couples classes and makes changes risky.

---

### **10. What are the drawbacks of using inheritance excessively?**

Excessive inheritance can lead to:

1. **Tight coupling** – Child classes depend too much on parent implementation.
2. **Fragile base class problem** – A small change in the base class can break many subclasses.
3. **Reduced flexibility** – Java doesn’t support multiple inheritance of classes.
4. **Harder testing and maintenance** – Deep hierarchies are difficult to understand and debug.

**Good practice:**
Use inheritance only for clear “is-a” relationships. For behavior reuse, prefer composition.

### **1. What is the purpose of `this` and `super` keywords?**

* **`this`** refers to the current object of the class.
  **Uses:**

  * To refer to current instance variables.
  * To call another constructor in the same class (`this()`).
  * To pass the current object as a parameter.

  ```java
  class Employee {
      private String name;
      Employee(String name) {
          this.name = name; // refers to current object
      }
  }
  ```

* **`super`** refers to the **immediate parent class**.
  **Uses:**

  * To call parent class constructors (`super()`).
  * To access parent’s methods or variables hidden by child class.

  ```java
  class Manager extends Employee {
      Manager() {
          super("John"); // calls parent constructor
      }
  }
  ```

**Interview Tip:**
Use `this` for current class context and `super` to interact with parent class context.

---

### **2. What happens if a subclass defines a static method with the same name as a parent’s static method?**

It is **method hiding**, not overriding.
Static methods belong to the **class**, not the object.
The method that gets executed depends on the **reference type**, not the object type.

Example:

```java
class A { static void display() { System.out.println("A"); } }
class B extends A { static void display() { System.out.println("B"); } }

A obj = new B();
obj.display(); // prints "A"
```

**Key point:**
Static methods are **resolved at compile time**, unlike overridden instance methods which are resolved at runtime.

---

### **3. Can you override a private or static method in Java?**

* **Private methods:** No, because they are **not inherited** by subclasses.
* **Static methods:** No, they are **hidden**, not overridden (as explained above).

So only **non-static, non-private** methods can truly be overridden.

---

### **4. What is object immutability? How do you create an immutable class?**

An **immutable object** is one whose state cannot be changed after creation.
For example: `String`, `Integer`, and other wrapper classes are immutable.

**Steps to create an immutable class:**

1. Declare the class as `final` (so it can’t be subclassed).
2. Make all fields `private` and `final`.
3. Don’t provide setters.
4. Initialize all fields through a constructor.
5. If any field is mutable (like a list), return a **deep copy** in getters.

Example:

```java
final class Person {
    private final String name;
    private final Date dob;
    public Person(String name, Date dob) {
        this.name = name;
        this.dob = new Date(dob.getTime());
    }
    public String getName() { return name; }
    public Date getDob() { return new Date(dob.getTime()); }
}
```

---

### **5. Explain how encapsulation helps in data hiding and security.**

**Encapsulation** bundles data (fields) and methods that operate on that data into a single unit (class), and **restricts direct access** using access modifiers.

**Benefits:**

* **Data Hiding:** Internal details are hidden; only controlled access is provided via getters/setters.
* **Security:** Prevents external code from putting the object in an invalid state.
* **Maintainability:** Changes to internal logic don’t affect external code.

Example:

```java
class Account {
    private double balance;
    public void deposit(double amount) { if(amount > 0) balance += amount; }
}
```

Here, you can’t set a negative balance directly — that’s encapsulation protecting object integrity.

### **6. What is a deep copy vs shallow copy in Java?**

| Type             | Description                                                                                                                                 | Example                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| **Shallow Copy** | Copies field values, but if the object contains references, only the references are copied. Both objects share the same referenced objects. | `clone()` default behavior              |
| **Deep Copy**    | Creates a completely new copy of the object and its referenced objects. Changes in one do not affect the other.                             | Manually clone or serialize sub-objects |

**Example:**

```java
class Address { String city; }
class Person implements Cloneable {
    String name;
    Address address;
    protected Object clone() throws CloneNotSupportedException {
        return super.clone(); // shallow copy
    }
}
```

---

### **7. How do you clone an object? Why is cloning considered a bad practice sometimes?**

You can **clone** an object by implementing the `Cloneable` interface and overriding the `clone()` method.

Example:

```java
class Employee implements Cloneable {
    public Object clone() throws CloneNotSupportedException {
        return super.clone();
    }
}
```

**Why cloning is discouraged:**

* It **breaks encapsulation** (copies internal object structure directly).
* It **throws checked exceptions** and needs `Cloneable` marker interface.
* The default implementation does a **shallow copy**, which may cause shared references and bugs.
* **Better alternatives:** Use a copy constructor or factory method.

---

### **8. What design patterns use OOP principles effectively?**

Some common design patterns that leverage OOP principles:

* **Singleton** – Ensures only one instance (uses encapsulation and static methods).
* **Factory Method** – Uses abstraction and polymorphism to create objects without exposing creation logic.
* **Observer** – Uses composition and interfaces to achieve loose coupling.
* **Decorator** – Uses inheritance and composition to add behavior dynamically.
* **Strategy** – Uses abstraction and polymorphism to change behavior at runtime.

**Interview tip:** Mention that design patterns **encapsulate best practices** and promote **reusability** and **flexibility**.

### **9. How does polymorphism work internally (method table / vtable)?**

When you use **method overriding**, Java uses **dynamic method dispatch** at runtime.
Internally:

* Each class has a **method table (vtable)** that maps method names to their addresses.
* When a subclass overrides a method, its entry in the vtable replaces the parent’s method.
* At runtime, the JVM looks up the actual method from the vtable of the object’s class — **not** the reference type.

Example:

```java
Parent p = new Child();
p.show(); // JVM looks up show() in Child's vtable
```

This mechanism enables **runtime polymorphism** in Java.

### **10. Explain the difference between “is-a” and “has-a” relationships.**

| Relationship | Meaning                   | Achieved By              | Example                  |
| ------------ | ------------------------- | ------------------------ | ------------------------ |
| **is-a**     | Inheritance               | `extends` / `implements` | `Dog` **is-a** `Animal`  |
| **has-a**    | Composition / Aggregation | Instance variables       | `Car` **has-a** `Engine` |

**Rule of thumb:**
Use **is-a (inheritance)** when you want to share behavior, and **has-a (composition)** when you want to reuse functionality without tight coupling.

**Interview answer:**
“I prefer *has-a* over *is-a* when flexibility and loose coupling are more important — composition makes code easier to modify and test.”

### **1. Explain the Collection hierarchy in Java (List, Set, Map).**

The **Java Collection Framework (JCF)** provides a unified architecture to store, manipulate, and access data efficiently.

#### **Hierarchy Overview:**

* The **root interface** is `Collection`, which is extended by:

  * **List**
  * **Set**
  * **Queue**
    (`Map` is a separate hierarchy, not part of `Collection` but still part of the framework.)

---

#### **1️⃣ List Interface (Ordered, Duplicates Allowed)**

* Maintains **insertion order**.
* Allows **duplicate elements**.
* Access elements by **index**.
* **Common Implementations:**

  * `ArrayList` → Fast random access, slow insertion/removal in middle.
  * `LinkedList` → Fast insertion/deletion, slower random access.
  * `Vector` and `Stack` → Legacy, synchronized.

**Example:**

```java
List<String> list = new ArrayList<>();
list.add("A");
list.add("A"); // duplicates allowed
```

---

#### **2️⃣ Set Interface (Unordered, No Duplicates)**

### **2. How does ArrayList grow internally?**

**Short Answer (for basic interviews):**

> “`ArrayList` increases its capacity by 50% each time it runs out of space.”

**Detailed Internal Explanation (for deeper interviews):**

* `ArrayList` maintains an internal array `Object[] elementData`.
* When you add an element and the array is full, `ensureCapacity()` is called.
* It creates a **new array** with capacity = `oldCapacity + (oldCapacity >> 1)` (i.e., 1.5x growth).
* Then it copies all existing elements to the new array using `Arrays.copyOf()`.

**Example:**
If capacity is 10 and you add the 11th element → new capacity becomes **15**.

**Code Reference (from OpenJDK):**

```java
int newCapacity = oldCapacity + (oldCapacity >> 1);
elementData = Arrays.copyOf(elementData, newCapacity);
```

**Interview Tip:**

> “This growth strategy balances between minimizing resizing operations and avoiding memory waste.”

### **3. Why is ArrayList not thread-safe? How can you make it thread-safe?**

**Explanation:**

* `ArrayList` is **not synchronized**, meaning multiple threads can modify it simultaneously, leading to **race conditions** or **ConcurrentModificationException**.
* It is designed for **single-threaded environments** for performance reasons.

**Ways to make it thread-safe:**

1. **Using `Collections.synchronizedList()`**

   ```java
   List<Integer> list = Collections.synchronizedList(new ArrayList<>());
   ```

   → Provides a synchronized wrapper around the list.

2. **Using `CopyOnWriteArrayList`**

   * Thread-safe alternative for concurrent reads and infrequent writes.
   * No need for explicit synchronization.

3. **Manual synchronization**

   ```java
   synchronized(list) {
       // safely iterate or modify
   }
   ```

**Interview Tip:**

> “`ArrayList` isn’t thread-safe because synchronization would slow it down unnecessarily. In concurrent scenarios, we use `Collections.synchronizedList()` or `CopyOnWriteArrayList`.”

### **4. When would you use CopyOnWriteArrayList?**

**Purpose:**
`CopyOnWriteArrayList` is a thread-safe variant of `ArrayList` where **all mutative operations (add, set, remove)** are performed on a **new copy of the underlying array**.

**Use Case:**

* When you have **many reads and few writes**.
* Suitable for **read-mostly concurrent applications**, e.g., event listener lists, cache snapshots, or subscription lists.

**How it works internally:**

* On each modification, a **new array** is created and replaced atomically.
* Iterators work on a **snapshot**, so no `ConcurrentModificationException`.

**Interview Example:**

```java
CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
list.add("A");
for (String s : list) {
    list.add("B"); // No exception
}
```

**Interview Line:**

> “`CopyOnWriteArrayList` trades memory for thread-safety and is ideal when reads dominate writes, since every write operation creates a new copy of the array.”

### **5. How does subList() method of List work internally?**

**Explanation:**

* `subList(fromIndex, toIndex)` **does not create a new list**.
* It returns a **view** (backed by the original list) — meaning changes in one reflect in the other.
* Internally, it returns an inner class `SubList`, which maintains references to the parent list, the offset, and size.

**Example:**

```java
List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5));
List<Integer> sub = list.subList(1, 4);
sub.set(0, 99);
System.out.println(list); // [1, 99, 3, 4, 5]
```

**Caution:**

* Structural modification (add/remove outside subList range) on the parent list invalidates the subList.
* This causes a `ConcurrentModificationException` when accessed later.

**Interview Line:**

> “`subList()` returns a backed view, not a copy. So modifications are reflected both ways. But modifying the parent list structurally while the subList is active can lead to `ConcurrentModificationException`.”

### **2. How does HashSet ensure uniqueness of elements?**

**Explanation:**

* Internally, `HashSet` uses a `HashMap` where:

  * Elements are stored as **keys**.
  * A constant dummy object (`PRESENT`) is used as the value.
* When you add an element:

  * Its `hashCode()` is computed to find the correct bucket.
  * Then `equals()` is used to check if an existing element is *logically equal*.
  * If both match, the element is **not added** (uniqueness enforced).

**Example:**

```java
Set<String> set = new HashSet<>();
set.add("Java");
set.add("Java"); // Ignored, duplicate
```

**Interview Answer:**

> “`HashSet` ensures uniqueness using the combination of `hashCode()` and `equals()`. The hash code locates the bucket, and `equals()` checks if the element already exists in that bucket before adding.”

**Pro Tip:**
If your class overrides only one of these methods incorrectly, duplicates may appear or valid elements might be lost.

### **3. How does TreeSet maintain sorting order?**

**Explanation:**

* Internally, `TreeSet` is backed by a **`TreeMap`**, which is implemented as a **self-balancing Red-Black Tree**.
* It maintains order based on:

  1. **Natural ordering** — if elements implement `Comparable`
  2. **Custom ordering** — using a `Comparator` passed during TreeSet creation

**Example:**

```java
Set<Integer> set = new TreeSet<>();
set.add(10);
set.add(2);
set.add(5);
System.out.println(set); // [2, 5, 10]
```

**How It Works:**

* On every insertion, `compareTo()` or `compare()` is used to place the element at the correct node in the tree.
* The Red-Black Tree ensures the tree remains balanced for efficient O(log n) performance.

**Interview Answer:**

> “`TreeSet` maintains elements in sorted order using a Red-Black Tree structure. It relies on the element’s `compareTo()` method or a custom `Comparator` to decide ordering.”

### **4. Why should you override both equals() and hashCode() when using Sets or Maps?**

**Core Concept:**

* In Java, the **contract** between `equals()` and `hashCode()` is critical for **hash-based collections** like `HashSet`, `HashMap`, and `LinkedHashSet`.

**Contract:**

1. If two objects are **equal** (`equals()` returns true), they **must have the same hashCode()**.
2. If two objects have the **same hashCode()**, they may or may not be equal (equals() confirms it).

**Why it matters:**

* `HashSet` and `HashMap` first use `hashCode()` to find the bucket.
* Then they use `equals()` to check if the object already exists.
* If you override one but not the other, the collection can behave incorrectly — duplicates might appear or valid lookups might fail.

**Example:**

```java
class Employee {
    int id;
    String name;
    // override equals but not hashCode -> HashSet may store duplicates
}
```

**Interview Answer:**

> “Because `HashSet` and `HashMap` use both `hashCode()` and `equals()` to ensure uniqueness and proper retrieval. If you override only one, your objects can break the collection’s behavior — for example, duplicates may appear in a `HashSet`.”

### **1. How does HashMap work internally? (hashing, buckets, collisions, resizing)**

**Interview Answer:**

> “`HashMap` stores key-value pairs using a hashing mechanism. It uses the key’s `hashCode()` to determine the bucket index where the entry will be stored. If two keys map to the same bucket, a collision occurs, which is handled using linked lists (or balanced trees from Java 8 onwards). When the number of entries exceeds a threshold (load factor × capacity), the map resizes by doubling its capacity.”

**Detailed Breakdown:**

* **Internal structure:**
  An array of `Node<K,V>` objects called **buckets**.
  Each bucket can hold a **linked list** (or **tree**) of entries.
* **Hashing:**

  ```java
  int hash = key.hashCode() ^ (key.hashCode() >>> 16);
  int index = hash & (n - 1);
  ```

  (This ensures even distribution across buckets.)
* **Collision Handling:**

  * Before Java 8 → handled by **Linked List**
  * After Java 8 → if a bucket has more than **8 entries**, it converts into a **balanced tree (Red-Black Tree)** for faster lookup (O(log n)).
* **Resizing:**

  * Default capacity = 16, load factor = 0.75
  * When size exceeds `16 × 0.75 = 12`, it doubles capacity to 32 and rehashes all entries.

**Example Workflow:**

1. Compute hash for the key.
2. Find the bucket index.
3. If bucket empty → add new node.
4. If bucket occupied → check equality with existing keys (using `equals()`).
5. If key exists → overwrite value; else → add new node.

---

### **2. What is the significance of hashCode() and equals() in HashMap?**

**Interview Answer:**

> “`hashCode()` determines which bucket an entry goes into, and `equals()` determines whether two keys in the same bucket are logically equal. Both methods together ensure that keys remain unique and can be retrieved efficiently.”

**Explanation:**

* When you put an entry:

  * HashMap calls `hashCode()` to locate the bucket.
  * If multiple keys land in the same bucket, it uses `equals()` to check equality.
* If two keys are *equal* (`equals()` returns true), the existing value is replaced.

**Key Contract:**

> “If two objects are equal, they must have the same hash code.”

**Violation of contract → unpredictable behavior**

* May lose entries.
* May allow duplicates in same bucket.

### **3. How does HashMap handle collisions before and after Java 8?**

**Interview Answer:**

> “Before Java 8, HashMap used a linked list to handle collisions, which had O(n) lookup time in the worst case. From Java 8 onward, when many collisions occur (bucket size > 8), HashMap converts the linked list into a Red-Black Tree, improving worst-case lookup from O(n) to O(log n).”

**Summary Table:**

| Version            | Collision Handling                  | Time Complexity (Worst Case) |
| ------------------ | ----------------------------------- | ---------------------------- |
| Java 7 and earlier | Linked List                         | O(n)                         |
| Java 8 and later   | Linked List → Tree (Red-Black Tree) | O(log n)                     |

**Conversion back:**
If entries drop below 6, it converts back to a linked list to save memory.

### **5. What is LinkedHashMap? How does it maintain insertion order?**

**Interview Answer:**

* Backed by a **HashMap + doubly linked list**.

**Interview Answer:**

### **7. What is ConcurrentHashMap? How does it achieve thread safety?**

**Interview Answer:**

> “`ConcurrentHashMap` is a thread-safe implementation of `HashMap` that allows concurrent reads and controlled writes without locking the entire map. It achieves concurrency by **dividing the map into segments (Java 7)** or **using fine-grained locks on bins (Java 8)**.”

**Internals (Java 8 and later):**

* Uses **CAS (Compare-And-Swap)** and **synchronized blocks on individual bins**, not the entire map.
* **Reads** are mostly **lock-free**.
* **Writes** (put/remove) use fine-grained synchronization at the bucket level.
* No `ConcurrentModificationException` during iteration.

**Key Differences from HashMap:**

| Feature               | **HashMap**     | **ConcurrentHashMap**          |
| --------------------- | --------------- | ------------------------------ |
| **Thread Safety**     | Not thread-safe | Thread-safe                    |
| **Null Keys/Values**  | Allowed         | Not allowed                    |
| **Concurrency Level** | N/A             | High (segment/bin-level locks) |
| **Iteration**         | Fail-fast       | Weakly consistent              |

**Interview Tip:**

> “`ConcurrentHashMap` is preferred over `Hashtable` or synchronized `HashMap` for multi-threaded environments because it allows better scalability and performance through fine-grained locking.”

### **1. What happens if you insert a key with same hashcode but different equals() result in a HashMap?**

**Interview Answer:**

> “If two keys have the same hashcode but are not equal according to `equals()`, they are treated as different keys. The HashMap will store them in the same bucket (collision), but as separate entries in a linked list or tree.”

**Example:**

```java
map.put(new Key(1), "A");
map.put(new Key(2), "B"); // same hashCode, different equals()

Both entries will coexist in the same bucket — the map size will increase.

**Follow-up Tip:**

> “This is why it’s important to ensure `hashCode()` and `equals()` are consistent — equal objects must have the same hashcode.”

**Example:**

> “That’s why classes like `String` and wrapper classes (`Integer`, `Long`, etc.) are safe and commonly used as keys — they are immutable and their hashcodes don’t change.”

### **6. How would you design your own custom immutable Collection?**

**Interview Answer:**

> “To design an immutable collection, ensure that its internal state cannot be modified after creation.”

**Steps:**

2. Declare all fields `private final`.
3. Don’t provide setters.
4. Return defensive copies of mutable fields.
5. Don’t expose internal references directly.

final class MyImmutableList {

    public MyImmutableList(List<String> input) {

        return new ArrayList<>(data); // defensive copy
    }
}
```

**Interview Tip:**

* **VisualVM**, **Eclipse MAT**, **JProfiler**, **YourKit** → Analyze heap dumps.
* Look for growing collections (like `List`, `Map`) holding unneeded references.

**Prevention:**

* Use **WeakReference** or **WeakHashMap** where appropriate.
* Clear or nullify collections after use.
* Avoid static collections unless necessary.

**Example:**

> “A static HashMap caching objects without removal can cause a memory leak.”

### **10. When would you use WeakHashMap in your projects?**

**Interview Answer:**

> “WeakHashMap is used when you want the entries to be automatically removed once their keys are no longer in ordinary use.”

**Explanation:**

* Keys are stored as **WeakReferences**.
* When a key is no longer referenced elsewhere, the GC automatically removes that entry.

**Use Cases:**

* Caching with automatic cleanup.
* Associating metadata with objects without preventing GC.

**Example:**

```java
Map<Object, String> map = new WeakHashMap<>();
Object key = new Object();
map.put(key, "data");
key = null; // entry automatically removed on next GC
```

**Interview Tip:**

> “It’s perfect for caches or registries where you don’t want keys to prevent garbage collection.”

### **1. Difference between synchronizedMap and ConcurrentHashMap**

| Feature                    | **synchronizedMap**                                                   | **ConcurrentHashMap**                                            |
| -------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **Thread Safety**          | Achieved by synchronizing the entire map                              | Achieved by segment-level or bucket-level locking (fine-grained) |
| **Performance**            | Slower — all threads block on the same lock                           | Faster — multiple threads can read/write concurrently            |
| **Null Keys/Values**       | Allows one null key and multiple null values                          | Does **not** allow null keys or values                           |
| **Fail-Safe or Fail-Fast** | Fail-fast — throws `ConcurrentModificationException` during iteration | Fail-safe — allows concurrent reads and updates                  |
| **Use Case**               | When you need a quick synchronized wrapper for legacy code            | For high-concurrency, thread-safe maps (production-grade use)    |

**Interview Answer:**

> “`Collections.synchronizedMap()` synchronizes all operations on a single lock, making it less efficient under heavy concurrency.
> `ConcurrentHashMap` uses segment-level locking and allows concurrent reads and partial writes, providing much better scalability.”

**Follow-up Tip:**

> “In modern multithreaded systems, we prefer `ConcurrentHashMap` over `synchronizedMap` for performance and non-blocking iteration.”

### **2. What are WeakHashMap and IdentityHashMap?**

#### **WeakHashMap**

* Keys are stored as **WeakReferences**.
* When a key is no longer strongly referenced elsewhere, **GC automatically removes the entry**.
* Used for **caching** or **metadata storage** where entries should vanish automatically.

**Example:**

```java
Map<Object, String> map = new WeakHashMap<>();
Object key = new Object();
map.put(key, "value");
key = null;
System.gc(); // Entry removed automatically
```

**Interview Answer:**

> “`WeakHashMap` is used when you want entries to disappear automatically once keys are no longer referenced — ideal for lightweight caches.”

---

#### **IdentityHashMap**

* Uses **reference equality (==)** instead of **logical equality (`equals()`)** for keys.
* Two different objects with same content are treated as different keys.
* Often used for **object graph processing, serialization frameworks**, or when you need **object identity-based mapping**.

**Example:**

```java
Map<String, String> map = new IdentityHashMap<>();
map.put(new String("Java"), "A");
map.put(new String("Java"), "B"); // treated as different keys
System.out.println(map.size()); // 2
```

**Interview Answer:**

> “`IdentityHashMap` compares keys using `==` rather than `equals()`. It’s useful in scenarios like serialization where true object identity matters.”

### **3. How does ConcurrentModificationException occur?**

**Explanation:**

* It occurs when a collection (like `ArrayList`, `HashMap`, etc.) is **structurally modified** (add/remove) while being **iterated** using an **Iterator**, without using the Iterator’s own methods.

**Example:**

```java
List<Integer> list = new ArrayList<>();
list.add(1); list.add(2);
for (Integer i : list) {
    list.remove(i); // Structural modification -> Exception
}
```

**Why it happens:**

* Iterators maintain an **internal modification count (modCount)**.
* If the collection’s modCount changes unexpectedly, it throws `ConcurrentModificationException`.

**Interview Answer:**

> “It occurs when a collection is modified while being iterated, breaking the iterator’s expected modification count. To avoid it, use concurrent collections like `CopyOnWriteArrayList` or use the iterator’s `remove()` method.”

### **4. What is the difference between Enumeration and Iterator?**

| Feature               | **Enumeration**                                        | **Iterator**                                   |
| --------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| **Package**           | `java.util` (legacy)                                   | `java.util`                                    |
| **Introduced In**     | JDK 1.0                                                | JDK 1.2                                        |
| **Methods**           | `hasMoreElements()`, `nextElement()`                   | `hasNext()`, `next()`, `remove()`              |
| **Remove Supported?** | ❌ No                                                   | ✅ Yes                                          |
| **Fail-Fast?**        | ❌ No (used with legacy classes like Vector, Hashtable) | ✅ Yes (throws ConcurrentModificationException) |
| **Use Case**          | Legacy collections                                     | Modern collections                             |

**Interview Answer:**

> “`Enumeration` is legacy and read-only, while `Iterator` is modern, supports element removal, and is fail-fast. For concurrent modifications, use `ListIterator` or concurrent collections.”

**Follow-up Tip:**

> “From Java 5 onward, we rarely use `Enumeration` except with old classes like `Vector` or `Hashtable`.”

### **5. What is a BlockingQueue and when would you use it?**

**Definition:**

* A `BlockingQueue` is a **thread-safe queue** that **blocks** when:

  * You try to **add** an element to a full queue.
  * You try to **remove** an element from an empty queue.

**Common Implementations:**

| Type                      | Description                          |
| ------------------------- | ------------------------------------ |
| **ArrayBlockingQueue**    | Fixed-size, bounded queue            |
| **LinkedBlockingQueue**   | Optionally bounded, linked nodes     |
| **PriorityBlockingQueue** | Ordered elements by priority         |
| **SynchronousQueue**      | No capacity; one-in, one-out handoff |

**Example:**

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(5);

new Thread(() -> {
    try {
        queue.put("Task");
    } catch (InterruptedException e) {}
}).start();

new Thread(() -> {
    try {
        String task = queue.take();
        System.out.println("Consumed: " + task);
    } catch (InterruptedException e) {}
}).start();
```

**Interview Answer:**

> “`BlockingQueue` is used in producer-consumer scenarios. It handles thread synchronization automatically — producers wait when the queue is full, and consumers wait when it’s empty.”

**Use Cases:**

* Producer-Consumer systems.
* Thread pools (`ThreadPoolExecutor` uses a `BlockingQueue` internally).
* Asynchronous message passing.
